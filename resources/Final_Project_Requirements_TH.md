# สรุปโปรเจกต์ปลายภาค Embedded System (CEDT) 2026: Smart Devices

## 1. ภาพรวมและเป้าหมาย

- สร้างอุปกรณ์อัจฉริยะ (Smart Device) โดยใช้ไมโครคอนโทรลเลอร์ (ESP32 หรือคล้ายกัน) อ่านค่าเซนเซอร์ ควบคุม actuator ส่งข้อมูลจาก sensor node ไปยัง gateway เชื่อมต่ออินเทอร์เน็ต/คลาวด์ และใช้ AI ตัดสินใจเพื่อควบคุมอุปกรณ์
- **ปีนี้เน้นคุณภาพงานวิศวกรรมระบบฝังตัว** (การออกแบบ firmware, ความน่าเชื่อถือของการสื่อสาร, การวัดประสิทธิภาพจริง) มากกว่าจำนวนฟีเจอร์
- เลือกหัวข้อเองภายใต้ธีม Smart Devices เช่น ตรวจวัดสิ่งแวดล้อม สุขภาพ/ดูแลผู้สูงอายุ ประหยัดพลังงาน ลดขยะ บริการในมหาวิทยาลัย
- ยืมเซนเซอร์/actuator จากรายวิชาได้ (ต้องคืนในสภาพใช้งานได้หลังนำเสนอ) ถ้าไม่มีต้องซื้อเอง และปรึกษาอาจารย์ได้
- ทำเป็นกลุ่ม **3–5 คน** และสมาชิกแต่ละคนต้องรับอย่างน้อย 1 บทบาท

## 2. ความรู้พื้นฐานและนิยามสำคัญ

**Smart device:** อุปกรณ์อิเล็กทรอนิกส์ที่เชื่อมต่อกับอุปกรณ์/เครือข่ายอื่นผ่านโปรโตคอลไร้สาย (Bluetooth, Zigbee, NFC, Wi-Fi, 5G) ทำงานโต้ตอบและอัตโนมัติได้ในระดับหนึ่ง

**แพลตฟอร์ม IoT/Cloud ที่ใช้ได้:** NETPIE (ต้องใช้ NETPIE2020 เท่านั้น บทเรียนเก่ามี API ที่ใช้ไม่ได้แล้ว), Firebase, ThingSpeak, Blynk, Google Sheets หรือ MQTT broker + ฐานข้อมูลของตนเอง

**นิยามที่ใช้ในเอกสาร:**

| คำ | ความหมาย |
|---|---|
| Sensor node | บอร์ดที่เก็บข้อมูลจากเซนเซอร์ของตัวเองเป็นหลัก **ไม่ส่งขึ้นคลาวด์โดยตรง** แต่ส่งให้ gateway |
| Gateway | บอร์ด (ESP32, Raspberry Pi ฯลฯ) ที่รวบรวมข้อมูลจาก sensor node และเซนเซอร์ของตัวเอง ประมวลผลแบบเรียลไทม์ ควบคุม actuator และส่งต่อขึ้นคลาวด์ ช่องทางสื่อสารระหว่าง node กับ gateway เป็นอะไรก็ได้ (Wi-Fi, ESP-NOW, Bluetooth, UART) |
| Gateway sensors | gateway ต้องมีเซนเซอร์ที่ต่อสายกับตัวเองด้วย นอกเหนือจากข้อมูลที่รับจาก node |
| ตำแหน่งเซนเซอร์ | โมดูลเซนเซอร์ (รวม I2C/SPI) นับให้บอร์ดที่ต่อสายอยู่ |
| ชนิดเซนเซอร์ | แต่ละชิ้นส่วนตรวจจับนับเป็น 1 ชนิด โมดูลที่วัดสองค่า (เช่น DHT22 อุณหภูมิ+ความชื้น) นับเป็น 1 ชนิด และเซนเซอร์เหมือนกันสองตัวก็นับเป็น 1 ชนิด |
| Off-the-shelf products | อุปกรณ์สำเร็จรูป (เช่น smart plug, IP camera) **ไม่นับ** เป็นเซนเซอร์/actuator ต้องต่อและควบคุมจาก node/gateway ของตนเอง |
| Actuator | อุปกรณ์ที่ทำให้เกิดการเคลื่อนที่/การกระทำทางกายภาพ เช่น มอเตอร์ DC, เซอร์โว, สเต็ปเปอร์, ปั๊ม, solenoid valve, solenoid lock, linear actuator **ที่ไม่นับ:** LED, RGB LED, buzzer, ลำโพง (รวมลำโพงพูดตอบ), จอแสดงผล, IR/RF transmitter |
| Cloud storage | บริการที่เก็บข้อมูลดิบจากเซนเซอร์และอ่านย้อนกลับได้ (NETPIE, Firebase, ThingSpeak, Google Sheets) บริการปฏิทินอย่างเดียวไม่นับ |
| AI component | โมเดล AI ที่ประมวลผลข้อมูลกล้อง ไมโครโฟน หรือเซนเซอร์แล้วตัดสินใจ ใช้โมเดล open-source/pre-trained ได้ ไม่ต้องเทรนเอง อินพุตเป็นข้อมูลเซนเซอร์ได้ **เกณฑ์ threshold หรือ if-else ไม่นับเป็น AI** เรียก LLM/vision model ผ่าน cloud API ได้ โมเดลรันบน MCU, gateway, คอมพิวเตอร์, มือถือ หรือ cloud API ก็ได้ (รันบน MCU ได้คะแนนข้อ E7) |

## 3. กลุ่มและบทบาท

- กลุ่มละ 3–5 คน; น้อยกว่า 3 คนต้องได้รับอนุมัติจากอาจารย์
- **เกิน 5 คน หักคนละ −2.5 คะแนนต่อสมาชิกที่เกิน**
- กลุ่ม 3 คนรวมบทบาทได้

**5 บทบาท:**
1. **System Architect & Integration** – ออกแบบระบบ data flow รูปแบบข้อความ และรวมทุกส่วนเข้าด้วยกัน
2. **Embedded Developer (Sensor Node)** – พัฒนา firmware บน sensor node
3. **Embedded Developer (Gateway & Cloud)** – พัฒนา firmware gateway ประมวลผลเรียลไทม์ และเชื่อมต่อคลาวด์
4. **UI/UX & Dashboard Developer** – ออกแบบและพัฒนา dashboard, แอปมือถือ/เว็บ, การแจ้งเตือน
5. **Project Manager & Test Lead** – บริหารเวลา วางแผนทดสอบ และเก็บค่าตัวชี้วัดประสิทธิภาพ

**ต้องเขียนบทบาทของทุกคนใน proposal และรายงานฉบับสุดท้าย และงานของทุกคนต้องปรากฏในประวัติ commit ของ Git**

### 4.3 กฎความปลอดภัย

- ไฟบ้าน 220 V AC สวิตช์ได้ผ่านโมดูล relay/SSR ที่ปิดมิดชิดและได้รับการรับรอง หรือ smart plug เท่านั้น **ห้ามมีสายไฟแรงสูงเปลือย** อุปกรณ์ที่ใช้ไฟบ้านต้องให้ TA หรืออาจารย์ตรวจก่อนสาธิต
- แยกของเหลว (ปั๊ม ถังน้ำ) ออกจากอุปกรณ์อิเล็กทรอนิกส์ทางกายภาพ และใช้ถาดหรือกล่องรองรับการหก
- แบตเตอรี่ลิเทียมต้องมีวงจรป้องกัน และห้ามชาร์จทิ้งไว้โดยไม่มีคนดู
- ชิ้นส่วนเคลื่อนที่ (มอเตอร์ ประตู ล็อก) ต้องมีวิธีหยุดอย่างปลอดภัย (limit switch, timeout หรือปุ่มหยุดด้วยมือ)

## 5. เกณฑ์การให้คะแนน (รวม 70 คะแนน)

### I. นิยามปัญหา (5 คะแนน)
- **ความเกี่ยวข้องและผลกระทบ (3):** อธิบายปัญหาจริงที่กระทบคนกลุ่มใหญ่ และชี้ความเร่งด่วน ปัญหาชัดเจนและขอบเขตเหมาะกับโปรเจกต์ระบบฝังตัว
- **หลักฐานและรายละเอียด (2):** มีที่มา บริบท และหลักฐาน (ข้อมูล การสัมภาษณ์ผู้ใช้ การสังเกต หรือเจ้าของปัญหาจริง)

### II. สถาปัตยกรรมระบบและการขยายตัว (5 คะแนน)
- **สถาปัตยกรรมและ data flow (2):** แผนภาพภาพรวมชัดเจน, กำหนดรูปแบบข้อความระหว่าง sensor node–gateway–cloud, ประมวลผลเรียลไทม์บน gateway เพื่อควบคุมทันที
- **Scalability (3):**
  - **1 คะแนน:** รูปแบบข้อความและโค้ด gateway รองรับหลาย node (เช่น มี node ID ในทุกข้อความ) แสดงในโค้ด
  - **2 คะแนน:** sensor node จริง 1 ตัว + node จำลองอย่างน้อย 2 ตัวทำงานพร้อมกัน gateway และ dashboard ระบุแยกแต่ละ node ถูกต้อง
  - **3 คะแนน:** sensor node จริงอย่างน้อย 2 ตัวทำงานพร้อมกัน

### II′. Embedded Engineering Depth (10 คะแนน)
เลือกจากเมนู แต่ละข้อ **2 คะแนน** (1 คะแนนถ้าทำได้บางส่วนหรืออธิบายไม่ได้ทั้งหมด) สูงสุด **5 ข้อ = 10 คะแนน** ทำเกิน 5 ข้อได้แต่คะแนนมีเพดาน 10 **ข้อจะนับก็ต่อเมื่อสาธิตและอธิบายวิธีทำได้** (ในรายงานและตอน Q&A) ต้องระบุข้อที่วางแผนทำใน proposal และเปลี่ยนภายหลังได้ (อธิบายการเปลี่ยนในรายงาน)

| # | หัวข้อ | สิ่งที่นับ |
|---|---|---|
| E1 | RTOS multitasking | FreeRTOS อย่างน้อย **3 task** พร้อมเหตุผลของลำดับความสำคัญ สื่อสารกันผ่าน queue, semaphore หรือ event group |
| E2 | Interrupt-driven I/O | อย่างน้อย 1 อินพุตจัดการด้วย ISR พร้อม deferred processing (ไม่ใช้ busy polling) |
| E3 | Low power | Deep/light sleep พร้อมวัดกระแสที่ใช้จริงและประมาณอายุแบตเตอรี่ |
| E4 | Reliable communication | Acknowledgement/retry ระหว่าง node–gateway และ store-and-forward (บัฟเฟอร์) เมื่ออินเทอร์เน็ต/คลาวด์ล่ม |
| E5 | Security | การเชื่อมต่อคลาวด์แบบเข้ารหัสและยืนยันตัวตน (เช่น MQTT over TLS พร้อม credentials) ไม่มี secret ใน repository |
| E6 | OTA update | อัปเดต firmware ผ่านอากาศ และสาธิตได้ |
| E7 | On-device AI | โมเดล AI รันบน MCU เอง (เช่น ESP32-S3 กับ TinyML, ESP-DL, Edge Impulse) |
| E8 | Low-level driver/protocol | เขียนไดรเวอร์เองระดับ register หรือ bus (I2C/SPI/UART) หรือโปรโตคอล multi-hop/mesh ข้าม **3 node ขึ้นไป** (เช่น ESP-NOW mesh, LoRa) การเชื่อมต่อ point-to-point ธรรมดาที่ใช้ทำ M3 **ไม่นับ** |

### III. การพัฒนา/Implementation (20 คะแนน)

- **Functionality (8):**
  - ฟังก์ชันหลัก (สูงสุด 4 คะแนน): ให้คะแนนตามจำนวนฟีเจอร์หลักที่ทำได้และสาธิตได้
  - ความสมบูรณ์ (+4): ฟีเจอร์ที่ออกแบบไว้ทั้งหมดทำงานครบตามที่ตั้งใจ
- **Field Testing (3):**
  - 1: ทดสอบขั้นต่ำในสภาพแวดล้อมของตนเอง
  - 2: ทดสอบต่อเนื่องในสภาพแวดล้อมของตนเอง พร้อมเก็บข้อมูลต่อเนื่อง **อย่างน้อย 24 ชั่วโมง**
  - 3: ทดสอบกับผู้ใช้จริงหรือสถานที่จริง (ติดตั้งมากกว่า 1 แห่งยิ่งดี)
- **Robustness (3):**
  - 1: ใช้ได้บางครั้ง
  - 2: ใช้ได้เกือบทุกครั้ง
  - 3: ใช้ได้ทุกครั้งในทุกเงื่อนไขที่ทดสอบ และ **กู้คืนตัวเองได้หลังไฟดับหรือ Wi-Fi หลุด**
- **Build Quality (3):** การจัดระเบียบ ความสวยงาม การพกพา
  - 1: เป็นแค่ต้นแบบที่ใช้งานได้
  - 2: ใส่ในโมเดลหรือกล่องอย่างเหมาะสม เคลื่อนย้ายได้ถ้าระวัง
  - 3: เดินสายเรียบร้อย ติดตั้งในกล่องที่สวย ขนย้ายและตั้งค่าได้ง่ายโดยไม่เสียหาย
- **User Experience (3):** dashboard/แอปและการแจ้งเตือน
  - 1: พยายามทำให้อินเทอร์เฟซดูดีและใช้งานได้บ้าง
  - 2: อินเทอร์เฟซชัดเจนเป็นระเบียบ (dashboard Blynk/NETPIE ที่จัดวางดีก็ยอมรับได้)
  - 3: ใช้งานง่ายและสวยงาม แทบไม่ต้องอธิบาย การแจ้งเตือนชัดเจนและมีประโยชน์

### IV. การทดสอบและการวิเคราะห์ (10 คะแนน)

- **Test Plan and Procedure (3):** มีขั้นตอนทดสอบเป็นเอกสาร ครอบคลุมการใช้งานปกติ edge case และเงื่อนไขล้มเหลว (Wi-Fi หลุด, ถอดเซนเซอร์, ไฟดับ)
  - 1: ทดสอบบางกรณี / 2: ปกติ + edge case / 3: รวมเงื่อนไขล้มเหลว พร้อมขั้นตอนและผลที่บันทึกไว้
- **Quantitative Metrics (4):** วัดอย่างน้อย **3 ตัว** จากรายการด้วยข้อมูลจริงและระบุวิธีวัด:
  - latency ปลายทาง (sensor → dashboard หรือ sensor → actuator)
  - packet delivery rate ระหว่าง node กับ gateway
  - ความแม่นยำเซนเซอร์เทียบกับเครื่องมืออ้างอิง
  - การใช้พลังงาน/อายุแบตเตอรี่
  - ความแม่นยำ AI (หรือ precision/recall) บนข้อมูลทดสอบของตนเอง
  - uptime ในการรันต่อเนื่อง
  - การให้คะแนน: ตัวละ 1 คะแนน (สูงสุด 3) บวก **1 คะแนน** เมื่อวัดซ้ำและรายงานค่าความแปรปรวน (เช่น ค่าเฉลี่ย และ min/max)
- **Analysis and Comparison (3):** วิเคราะห์และเปรียบเทียบผลกับเป้าหมายโปรเจกต์และกับผลิตภัณฑ์/ระบบที่มีอยู่
  - 1: เทียบกับเป้าหมาย / 2: เทียบกับระบบที่มีอยู่ด้วย / 3: ทั้งสองอย่างโดยใช้ตัวชี้วัดที่วัดได้จริง
